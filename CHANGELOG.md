## [Unreleased]

### Added

#### Providers
- Per-provider `headers` (`providers.<name>.headers`) — an optional string→string map of extra HTTP headers on that provider's inference calls, for a unified OpenAI-compatible proxy in front of upstreams that need request headers lele cannot know about (the motivating case: OpenCode Go answers `400 MissingSessionID` — validated before authentication — to any call without `x-opencode-session`, and a provider pointed at a router is never detected as Go). Applied on both transports (OpenAI-compatible `chat/completions`, Anthropic Messages `messages`), streaming and non-streaming, on every call; never on model listing (`GET /models` — neither the live fetch nor the onboarding check) or catalog prefetches. The families that build their own clients — Claude/Codex OAuth, `claude-cli`/`codex-cli`, Gemini Code Assist, GitHub Copilot — never read the map, so switching one of those entries to OAuth (`auth_method: oauth`/`token`) silently stops sending the headers: configure the map on the provider whose transport can carry it. Custom headers are applied **last** — after the transport defaults (`Content-Type`, `User-Agent`, `Authorization`/`X-Api-Key` plus `Anthropic-Version`) and after the auto-detected session header — so an explicit entry wins, including `Authorization` (a gateway whose scheme is not `Bearer`) and `x-opencode-session` itself. Values carry two legal placeholders: `{{session}}`, expanded per call to the same 64-hex value lele already sends natively — the SHA-256 of the conversation session key, stable across turns and restarts, changed by `/new`, and the shared unkeyed bucket for calls with no session key, so the token always resolves to a non-empty id the gateway can route on (Go would send an empty value without complaint, but an empty `x-opencode-session` defeats the gateway's session routing and it answers its own opaque 400); and `{{ENV_NAME}}`/`{{ENV_NAME:default}}`, the env placeholder `config.json` already supports, so a gateway token never has to sit in the file — the validator only recognises the shape and the value is expanded when the config is loaded (a missing variable with no default becomes empty), which is why the editable settings document echoes the raw token and a WebUI save accepts it back unchanged. Any other `{{…}}`, and an unterminated `{{`, is a config error. The map is validated when the provider JSON is decoded — `config.json` load and every reload, and a rejected reload leaves the running config untouched — aborting with the provider and the header named: names must be RFC 7230 tokens, values must contain no CR/LF/NUL, and transport-owned headers are rejected (`Host`, `Content-Type`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Keep-Alive`, `Proxy-Connection`, `Upgrade`, `TE`, `Trailer`). The editable settings document is checked field by field as well, so `POST /api/v1/config/validate` and a rejected `PUT /api/v1/config` report `providers.<name>.headers` with code `invalid_header` — pointing at the culprit provider instead of a global config error the WebUI cannot place — while the decode-time check stays as the backstop. `config.json`/API-only for now: neither UI exposes an editor, but both preserve the map when they write other provider fields — the TUI mutates the loaded runtime config, and the WebUI settings document models the field and round-trips it, so a save from the browser rewrites the providers block with it.
- Per-model `thinking_type` (`providers.<name>.models.<alias>.thinking_type`) — names the wire-level "think system" a model's endpoint uses to turn reasoning on/off (`auto`, `deepseek`, `openai`, `openrouter`, `qwen`, `none`). Makes `thinking_level: "off"` actually disable reasoning on endpoints that default thinking on and ignore the generic `reasoning` object (DeepSeek V3.2+, Xiaomi MiMo, Zhipu GLM-4.5+ → `thinking: {"type": "disabled"}`; Qwen3/DashScope → `enable_thinking: false`; o1/o3 → never send thinking params with `"none"`). With `"auto"` (or unset) known thinking-object model families (`deepseek`, `mimo`, `glm` in the name) get the explicit disable for free.
- `thinking_type` is editable from both UIs: the TUI asks for a "Think system" when adding a provider/model (`/connect`, `/providers`), and the Web UI exposes a per-model **Think system** dropdown in the provider settings model editor.

#### Agent
- Subagent task retention (`agents.defaults.subagent_retention_minutes`, default 5 minutes) — a finished subagent task (`completed`, `failed`, `cancelled`, `not_done`) is now reaped from memory — and its `native:<parent>:subagent-N` session evicted from RAM — once it has been terminal for longer than the retention window; nothing is deleted, the session rows stay in SQLite and the session reloads on demand. Until now `CleanupTerminalTasks` only ran when *another* subagent was spawned, so a chat that had stopped spawning kept every finished task and its session resident forever, which is what made the TUI slower and slower as subagents accumulated. A periodic sweeper (once a minute — a poll cadence, not the window) does the reaping even when nothing new is spawned, it is idempotent (one goroutine per manager, reused across config reloads), and it re-reads the window on every pass. The value is carried in the editable config document, so the Web UI settings page and `config.json` round-trip it; `0` (and any negative value) keeps the 5-minute default rather than disabling the sweep, on purpose: an unset knob must never let the task map grow without bound again. The sweeper is stopped with the agent loop, with a bounded join: a sweeper that cannot stop in time is *detached* (it stops sweeping, and the session layer stays alive) instead of having the store closed under a write that is still in flight.
- Long-term memory writes go through a new `update_memory` tool (`agents.defaults.memory_max_lines`, default 500) — the agent appends a fragment (`mode: "append"`, the default) or rewrites the workspace `MEMORY.md` (`mode: "replace"`) instead of being told to write the file path directly; the system-prompt identity rule now points at the tool by name. Every write is validated before it lands: the resulting file is line-capped at `memory_max_lines` (an over-cap write is rejected with nothing written, and the error tells the agent to compact by rewriting the whole file with `replace`), hard-capped at 512 KiB regardless of line count — the line cap alone cannot stop flooding, because a single arbitrarily long line passes any line count and `MEMORY.md` is inlined into every system prompt — confined to the workspace when `restrict_to_workspace` is on (a symlinked `MEMORY.md` resolving outside the workspace is denied exactly like `write_file`/`append_file` deny it), and serialized under a tool-level mutex so concurrent appends from the parent and its subagents — which share the tool instance — cannot lose updates or race the cap checks. `<= 0` resolves to the 500-line default; the knob round-trips through the editable config document (WebUI settings, `config.json`, env `LELE_AGENTS_DEFAULTS_MEMORY_MAX_LINES`); and a malformed (non-string) `mode` argument is now an error instead of being silently accepted as an append.

#### TUI
- `/connect` opens a provider picker first — the free-text "type" step is no longer the entry point. Each row carries its own flow, dispatched by row kind (never by label): a known provider asks only for its API key and saves on the same Enter, OpenAI-compatible / Anthropic-compatible entries keep the full flow (base URL, key, model steps), and the OAuth-capable providers (Claude subscription, ChatGPT/Codex, Gemini Code Assist) start their native login **inside the same modal** instead of shelling out. The modal shows the authorization URL, `ctrl+y` copies it (OSC 52 plus the platform helper), and a paste field accepts the callback URL or the bare code, so the login completes without leaving the TUI and without blocking the Update loop — the engine drives the flow in the background and the TUI polls it. `esc` cancels and returns to the picker (`q` is ordinary text in the paste box, not a dismiss key), a failed exchange stays retryable, and success persists the credential plus the provider entry and hands off to the existing model wizard. The modal is height-clamped: on a short terminal it drops the optional instructions and then clips the URL with an explicit "clipped, ctrl+y to copy" marker, but never the paste box or the `esc` hint.
- Queued-message preview band — when the composer is parked behind a busy turn, a band above the process indicator shows the pending depth plus the *next* message to be sent (the FIFO head), dimmed and truncated to the pane width. The queue no longer shares the status line with the process state: that strip (count + `alt+delete`/`alt+enter` hints) is gone, so the loading indicator reads on its own line and the pending count is stated once, in the band. Reading order now matches chronology: waiting work above, running turn below. The band costs a line only while it has something to say — the viewport budget measures the rendered string, so an idle queue keeps the transcript its full height. Multi-line payloads collapse to a single sanitized line (control sequences stripped, tabs expanded, single-line, width-truncated).
- **MCP servers can be added by hand from the TUI** (`/mcp` → `N`) — a step-by-step wizard collects a name, the transport (`stdio` or `remote`, each with its own step set: command/args/env vs url/type/headers), an optional description and the target layer (global/agent/project), then writes through the same `mcp.UpsertEntry` seam as `lele mcp add` and the WebUI raw editor — same layering, validation and `${VAR}` rules (values are kept verbatim, never expanded). Env/headers values are masked as they are typed and only key names are shown afterwards (`KEY=•••••`); the review step surfaces the layered file's reality (an existing entry is *replaced* only after an explicit `yes`, and a copy in a higher layer that would shadow the new entry is called out), and the list reloads with the cursor landing on the new row. OAuth entries are out of scope in the wizard (`lele mcp add --auth oauth`).

- **The host can be kept awake from `/settings › Interface`** (`tui.keep_awake`, off by default) — a new *Keep device awake* row inhibits idle- and sleep-triggered suspend while the TUI runs, using a real per-platform mechanism: `systemd-inhibit --what=idle:sleep` on Linux (requires systemd; the wrapped `kill -0` loop makes the inhibition **self-release within 5 s even if lele is SIGKILLed**, as long as lele's parent reaps it (an unreaped zombie keeps `kill -0` answering)), `caffeinate -dims -w <pid>` on macOS (the `-w` assertion drops by itself when the process exits) and `SetThreadExecutionState(ES_CONTINUOUS|ES_SYSTEM_REQUIRED|ES_DISPLAY_REQUIRED)` on Windows, applied on a dedicated `LockOSThread`ed goroutine because that state is per thread. Closing the lid still suspends on purpose (`handle-lid-switch` is deliberately not inhibited). The mechanism runs in its own process group, so tearing it down kills the wrapper *and* the shell loop it spawned: `Stop` costs ~1 ms in the normal case and leaves nothing orphaned unless the group is wedged in uninterruptible sleep (a plain `SIGTERM` to the wrapper alone would leave the loop holding the stderr pipe and stall the wait out to its 3 s grace). A start is only reported as successful after the mechanism has survived a 250 ms readiness window (the Unix starters; Windows verifies synchronously), so the container/WSL2 case where `systemd-inhibit` is installed but cannot take the lock (it prints `Failed to inhibit …` and exits) surfaces the platform reason instead of a `✓` that lies. The persisted value is the *intent* while the row shows the *effective* state, in three glyphs: `✗` not requested, `✓` really held, `⚠` requested but not held. `ENTER` toggles when the inhibition is held and **retries** (without dropping the request) when it is not, so the first corrective keypress cannot silently throw the request away; `d` cancels the request deliberately. The failure reason rides the same list, sanitized and truncated to the modal budget — a 100-cell Go error can no longer widen the box past the frame and swallow its right border. Releasing is bound to the model (`Close()`), so `ctrl+c`, `/quit` and a render error all drop it, and a later launch retries the request. Known limitation: a mechanism that dies *after* a successful start (logind restarting, say) is not re-detected — the row keeps `✓` until the next toggle, deliberately, because probing the OS on every frame costs more than the failure it would catch.

#### Session
- Active turn resume (`session.resume_enabled`, default off) — when the gateway restarts mid-turn, the durable inbound replay now *resumes* the interrupted turn from a checkpoint instead of re-running it from scratch. Each in-flight inbound turn is checkpointed to the session-state KV (`sess:turn:<key>`: phase, iteration, agent, model, dedupe id); a replayed message whose dedupe id matches its checkpoint re-enters the loop with the user message already in history (no double-append, no duplicate work). Turns interrupted mid-tool-execution continue safely: pending tool calls are healed into "no recorded result" tool messages and the model decides whether to re-run them, instead of the executor blindly repeating side effects. Subagents that died with the process are snapshotted alongside the checkpoint and the model is warned on resume that their results are unavailable. Requires `session.durable_inbound` (the replay is the resume trigger).

#### MCP
- Model Context Protocol client support — `mcp.json` is discovered in three layers (global `<LeleDir>/mcp.json` < agent workspace `<AgentWorkspace>/mcp.json` < project `<cwd>/.lele/mcp.json`, merged by server name with the highest layer winning; the agent layer is disabled when `agents.defaults.workspace` is unset, it never falls back to the CWD) and configured servers reach the model only as a `## MCP Servers` context block of **name + description** — no tool schemas are injected until they are needed. The `load_mcp_tools` tool loads one server's specs on demand, registering them as `mcp_<server>_<tool>` (sanitised, 64-char cap with FNV suffix for collisions). Transports: stdio, Streamable HTTP and legacy SSE (`github.com/mark3labs/mcp-go` v1.1.1), with `${VAR}` / `$$`-escaped expansion in `env` and `headers`, lazy connect behind single-flight, reconnect-once on transport failure (the config is re-resolved right before the redial so a stale snapshot cannot reinstall a dead connection), and `"disabled": true` to park a server without deleting it. Architectural guards, pinned by tests: `pkg/tools` never imports `pkg/mcp` (the loader interfaces live in `pkg/tools`), and `pkg/mcp` receives paths as strings — it imports neither `pkg/config` nor `os.Getwd`. Full documentation in `docs/mcp.md`; verified with 66 package tests plus an out-of-repo end-to-end harness running the production binary against real stdio/HTTP/SSE servers (28 checks, 12/12 mutation battery).
- **MCP servers are now manageable from all three surfaces** — a layered inventory (`pkg/mcp/inventory.go`) reports, per server name, which layer **wins** (`global` < `agent` < `project`, the canonical order of `mcp.Layers()`), which copies are **shadowed** by it, and the effective verdict (`enabled` / `disabled` / `invalid`), reading every layer file **without expanding `${VAR}`** so nothing a UI lists can leak a resolved secret (env and headers are surfaced as key **names** only; `command`/`url`/`description` stay the raw stored bytes). Five authenticated routes expose it (`pkg/channels/rest_mcp.go`): `GET /api/v1/mcp` (inventory), `GET`/`PUT /api/v1/mcp/{layer}/raw` (one layer file verbatim, ≤1 MiB, validated by the same gate the runtime uses before anything is written), `PUT /api/v1/mcp/{layer}/servers/{name}/toggle` (`enabled` means **SET**, not flip; `?force=true` to overwrite a losing copy in the addressed layer) and `POST /api/v1/mcp/validate` (dry-run: a fatal envelope error vs per-entry warnings). Edits go through an order-preserving writer (`pkg/mcp/write.go`) that splices into the exact bytes of the envelope holding the target and saves atomically at `0600`, then fires **one** resync of the running agent's MCP servers through a narrow seam (`SetReloadMCP`, wired in `cmd/lele/gateway.go`) so a toggle takes effect without restarting the gateway. The TUI gains `/mcp` (filter by layer, space/t to toggle, enter for a read-only detail of the whole stack, rendered from the snapshot the list was built from — it never re-reads the disk under a pending keypress). The WebUI manages the same data on the agent config page, including a per-layer raw JSON editor with validate-before-save, dirty-state warnings and the `aliased_with` surfacing of layers that resolve to the same physical file. Invalid entries are not toggleable anywhere and point at the raw editor; `docs/mcp.md` + `docs/client-api.md` document the contract.

#### WebUI
- **Stored secrets can be edited instead of deleted and re-typed** — `/secrets` could create, reveal and delete a secret but not change one, so fixing a description, retagging, rescoping or rotating a value meant deleting the entry (and any agent referencing it by name seeing the secret disappear in the meantime). Every card now has an *Edit* button that opens the same form prefilled with the secret's metadata; the name is shown read-only (it is the keyring key, not a label) and an empty value means **keep the stored secret**, so a metadata edit never round-trips the plaintext through the browser and picking a new scope or tag cannot accidentally blank the value. A typed value replaces it. Backend: a new `PUT /api/v1/secrets/{name}` edits an existing secret and refuses to create one (`404` when the name is gone, so a stale card cannot silently resurrect a secret deleted from another surface), implemented by `keyring.Service.UpdateFromUI` — unlike the create path it preserves `CreatedAt`/`CreatedBy` and an empty value keeps the stored one. The create endpoint keeps its create-or-update contract, so the TUI (`/secrets` → *Add*) is untouched.
- **The Add-provider screen can no longer hide a provider the backend supports** — the wizard kept a hand-maintained `PROVIDER_TYPES` array next to `catalog.hardcodedProviderIDs`, so wiring a provider in Go did not make it selectable: PR #403 had to add `opencode`/`opencode_go` by hand after PR #395 shipped them backend-side, and 28 backend-known ids (`vercel`, `xai`, `lmstudio`, `ollama_cloud`, `huggingface`, `stepfun`, `minimax`, `mistral`, `together`, `fireworks`, `cerebras`, `gmi`, `arcee`, `novita`, `shengsuanyun`, `nanogpt`, `perplexity`, `siliconflow`, `chutes`, `nous`, `vllm`, `qwen_portal`, `tencent_tokenhub`, `xiaomi`, `kimi_for_coding`, `alibaba*`, `bedrock`, `azure_foundry`) stayed unselectable (issue #404). The tile grid is now `curated ∪ catalog` for real: the curated array only keeps what the catalog cannot supply — a product label (`OpenCode Zen` vs `OpenCode`) or a deliberate endpoint override — and everything else comes from `GET /api/v1/catalog/providers`. That endpoint now always carries an `api_base` (the hardcoded `catalog.DefaultAPIBaseByType` table fills the gaps a stale disk index leaves) plus a `base_less` flag for the providers whose endpoint cannot be derived (`custom`, `claude-code`, `codex-cli`, `bedrock`, `azure_foundry`), so a catalog-only tile pre-fills its endpoint instead of an empty field the user had to complete by hand. `GET /api/v1/providers/{name}/models` also answers for a provider that is not configured yet when the catalog knows it (`source: "catalog"`), so the model picker is populated before the provider is saved; an unknown name is still a `404`. Drift now fails CI instead of reaching a user: `TestCatalogProvidersEndpointServesEveryKnownType` (Go) asserts every `catalog.KnownProviderTypes()` id is served with an endpoint, and `TestProvidersCarryAPIBaseForEveryKnownType` (Go) asserts the complement — a new id without a default endpoint must be declared base-less explicitly.

### Changed

#### CLI
- **`lele agent -m "..."` prints the answer again** — the direct (no-bus) path processed the turn with the gateway's delivery contract: `runAgentLoop` published the final text to the outbound bus — which the one-shot CLI never subscribes to — and returned `""`, so stdout carried an empty reply while the real answer lived only in `lele.db`. `ProcessDirect` now runs the turn with an explicit `sendResponse=false` and RETURNS the final text; `ProcessDirectWithChannel` (cron/heartbeat, whose delivery *is* the publish) keeps its contract untouched. The two contracts and the cron delivery coordinates are pinned by `pkg/agent/message_processor_direct_test.go`, including a tripwire test for the known limitation that side deliveries (goal continuation, `/compact`, tool approvals, `SYSTEM_SPAWN` results) still travel over the bus and remain invisible to a plain CLI run.

#### TUI
- **Long chats are no longer slower per frame** — the per-frame cost used to grow with the conversation and is now flat: at 6000 messages an idle, streaming or mouse-motion frame went from ≈3.2 ms and 4.5 MB to ≈1.9 ms and 0.96 MB, and a 40-message chat costs the same ≈1.9 ms (both measured with the `make bench` harness; full before/after table and method in `docs/perf/tui-long-chat-results.md`, frozen "before" in `docs/perf/tui-long-chat-baseline.md`). The remaining ≈1.9 ms is the fixed cost of painting a full frame, independent of the history.
- **The history view is O(1)** — `GetHistoryView` is documented as a read-only view, but it copied the whole message slice on every call (≈328 µs and 1.16 MB at 6000 messages, three times per frame: the viewport rebuild plus the token/context readout of the bottom bar and the sidebar). It now returns a read-only snapshot that writers publish copy-on-write, tagged with the save epoch every mutation already bumps, so a publication that was missed or superseded only costs a lazy rebuild — never correctness; the snapshot is a private copy rather than a header aliasing the live array, because messages are mutated in place. Streamed chunks deliberately leave the snapshot stale instead of paying a copy per token, and the reader rebuilds it once per read burst.
- **A frame reads the history once and rebuilds only when something changed** — `View()` no longer rebuilds the viewport on every frame (bubbletea calls it after every update, so the streaming throttle had lost its meaning); it now compares an O(1) fingerprint of the model state the viewport content depends on, plus the layout geometry, and reaches the rebuild only when one of them is stale — which is also what makes a single streamed chunk cost one rebuild per throttle window. Every consumer of a frame (viewport, token/context readout in both places, pending-message checks) reuses the frame's single history read, the user+assistant count is memoized per snapshot, and the per-message render cache (keyed by a rewritten, allocation-free content fingerprint) never stores the transient render of the message whose tool is currently executing, so a cached frame can no longer keep suppressed tool rows after the message stops being the last one.
- **Subagent and session listings are cached and coalesced away from the render path** — the sidebar and the status line now serve a subagent listing refreshed at most once every 3 s from the update loop (one lookup costs 2.0 ms / 414 KB at 200 subagents, and 6.9 ms / 1.2 MB when those sessions are cold; it used to run from the render path and be invalidated by every lifecycle event), and the session walk behind `reloadSessions` — 444 µs / 179 KB / 815 allocations at 200 sessions, previously fired per completed turn, per tab and per sidebar click — runs at most once every 250 ms, coalescing bursts. Both keep the paths that must be exact exact: a switch onto a chat the snapshot does not know, and the `/sessions` picker, bypass the window; resident sessions are held by live pointer, so no message content is ever stale, and the batched store-side message counts are memoized on top of an exact cold-key check so the chat on screen always reports its real count.
- **Persistence no longer holds the write lock across its I/O** — the full rewrite, the excluded-range write, the eviction-boundary write and the metadata/incremental/delete saves collected a snapshot, then ran every SQLite round trip *and* every JSON encode/decode with the lock released before re-acquiring and reconciling through the existing save-epoch guard. Because frames take the read lock, each compaction and each metadata write used to freeze them for the whole write. The release/re-acquire now goes through one helper whose contract makes a panic in the I/O unable to leave the lock free for the caller's deferred unlock, and the I/O payloads are free functions with no access to the lock at all.
- **Eviction no longer cascades once per session inserted** — materializing a session ran the LRU pass immediately, so a burst of subagent sessions paid one full cascade (sort, save, full rewrite) per insertion. A 16-session hysteresis band now batches the pass: the whole backlog is evicted in one go when the resident set reaches its limit plus the band, ~16× fewer cascades in a 200-session burst, with the resident peak still bounded and every evicted session still saved exactly once.
- **`/compact` invalidates only what it changes** — the compact handler used to drop the per-message render cache and invalidate the rendered base unconditionally, re-rendering the whole visible window through markdown rendering for messages nothing had touched: 21.7 ms and 8.9 MB per compaction result, now 1.3 ms and 630 KB. What compaction really moves is already part of the cache keys (archived fingerprint, resident length and count, streaming flag), and the one render a fingerprint could not vouch for is not cached in the first place.
- **The idle status line reports background work and nothing else** — while subagents ran in the background with the parent idle, the line read `2 subagent(s) running in background — input is free`: a note about the composer, on every idle frame, telling the user something the composer already proves by accepting the keystroke. The trailing hint is gone from all three builtin locales (and therefore from the packs that fall back to them), so the line carries just the count. `TestSubagentsRunningText_ReportsOnlyBackgroundWork` pins the shape across every available locale — it must open with the count and must not carry a separator-followed hint or composer wording — so a future translation cannot smuggle the chrome back in.

#### Session
- Compaction/eviction now preserves the last 2 human turns and the original request verbatim — `ExcludeOldMessagesFromContext` pins index 0 plus the most recent `preservedUserMessages` (2) human user turns so they never enter the excluded range, even when `keepCount` would otherwise include them. Synthetic-injected messages (`[System:`, summary headers, retry guidance) are filtered out of the preserved-user count so only genuine human turns consume the two slots. With in-memory eviction enabled (default), the pinned turns that sit inside the evicted region leave the RAM slice and their verbatim text is folded into the session summary (`foldEvictedIntoSummary`); they reach the model inside the summary block, not as standalone messages.
- **Compaction keeps whole tool groups in the tail instead of emptying it** — when the kept tail would start with a `tool_result` whose owning `assistant` is about to be excluded, the anti-splice guard in `ExcludeOldMessagesFromContext` now moves the boundary **back** to that owner, located by `ToolCallID` within a bounded window (`K=8`; when no owner is found in the window the boundary falls back to the start of the result run and `HealToolCallPairs` heals any orphan at request time), so the whole tool group stays in context. The previous forward-push walked the boundary to the very end of the history on the degenerate shape (an `assistant` turn with N tool calls followed by their N results, with a small `keepCount`): compaction then emptied the requested `keepCount` tail — only index 0 and the pinned human turns still survived, the #340 no-emptying invariant — and the invariant reduced eviction to a no-op that left excluded rows resident in RAM round after round, while the cold-load fallback could leave an orphaned `tool_result` at `resident[0]`. Moving the boundary back removes both costs — no excluded row stays resident (measured `excluded_resident` 4–12 → 0) and, whenever the owner is found within the window, no orphan is produced — at the price of keeping the group live in context; in the fallback branch (owner absent or beyond the window) the run is kept as-is and `HealToolCallPairs` drops any orphan at request time, so nothing orphaned reaches the provider. The token overhead was measured per layout before adopting the policy (#343): at most 2412 tokens = 1.88% of the 128k window, well under the compaction threshold.

#### Native
- Rate limiting on native routes is now opt-in — disabled by default, configurable via `channels.native.rate_limit` (config file, WebUI, and `LELE_CHANNELS_NATIVE_RATE_LIMIT_*` env vars).  Set `enabled: true` to restore the legacy per-source-IP budgets (10 PINs/min, 5 pairings/min, 20 token refreshes/min, 120 API requests/min, 120 WebSocket messages/min); individual fields can be overridden and `0` or omitted means the built-in default.  The change was motivated by a browser with several tabs continuously refreshing tokens and signing itself out when the limits were hard-coded.  A stock install binds all interfaces (`0.0.0.0`), so the unauthenticated `POST /api/v1/auth/pair` endpoint (6-digit PIN, 5-minute expiry) loses its only brute-force control when the feature is off; a non-loopback bind with rate limiting disabled now logs a startup warning suggesting `channels.native.rate_limit.enabled=true`.  Enable it on any network-reachable install.

#### WebUI
- **The secret scope is now picked from the agent roster instead of typed** — creating a secret (`/secrets` → *New*) asked for its scope as a free-text, comma-separated list of agent IDs, so a typo silently scoped a secret to an agent that does not exist. The field is now a chip multi-select — one chip per configured agent, built from the app's live agent list (`GET /api/v1/agents`, the same source the sidebar uses) and reusing the `AgentChipMultiSelect` the per-agent *Subagents* tab already ships. No selection still means "all agents" (`scope: []`), an empty roster shows an explicit empty state instead of a bare input, and the value is carried as `string[]` end to end (the old `scopeText`/`.split(',')` parsing is gone). Each chip is a keyboard-toggleable `role="checkbox"` and the group carries the field's accessible name, so the control does not depend on a pointer.

### Fixed

#### TUI
- **Quitting the TUI no longer waits for the running turn to finish** — `ctrl+c` and `/quit` returned the terminal only after the in-flight agent turn had completed, because the exit path joined the loop's turn goroutines unbounded and the root context that would have aborted them was cancelled *after* the join. A long streamed answer therefore kept the shell frozen for the rest of the response (measured: 11.5 s to exit while a 15 s answer was streaming, and it grows with the answer; an idle exit was already ~20 ms). The teardown is now ordered like the gateway's: release the keep-awake inhibition, cancel the root context — which is what actually kills the provider stream, and any tool waiting on it — and only then join, with a bounded `tuiExitJoinGrace` (2 s) so a turn that ignores cancellation cannot hold the terminal hostage either (the teardown is abandoned, the store is left open and SQLite recovers the WAL on the next start, exactly like the `finalTurnJoinGrace` path). Same trade-off pressing ESC twice already made: the aborted turn's partial answer is discarded and the user message stays in history. Measured after the fix: 11.5 s → 0.02 s with a turn streaming, on both quit keys, idle unchanged. The grace is now a bound on the *whole* teardown rather than on each of its stages: `StopWithin` takes one deadline up front and passes every stage (the subagent retention sweepers, the turn join and the group-run drain) only what is left of it, so a stage that is slow but healthy can no longer spend the budget of the one after it and stretch the promised bound to a multiple of itself (`tuiExitJoinGrace` for the TUI, `finalTurnJoinGrace` for the gateway). A stage that finds the budget already spent is abandoned exactly like one that ran out mid-wait, leaving the store open for the next start.
- **System notices render as a tool card, not as the user's own text** — a background subagent result and every other runtime notification are persisted with role `user` and the canonical `[System: <sender>] <body>` prefix, so the transcript showed them as a `Tú`/`You` bubble: the TUI was attributing to the human text they never typed, and the raw marker leaked as content. They now go through a card shaped like a tool call (header `System notice: <sender>` plus the body in the existing tool-result box), the same treatment the Web UI gives them via its synthetic `system_notice` tool (#391). The parser mirrors the backend/web rule — the marker only counts at the start of the content and an empty sender is not a notice — so a user message that merely mentions `[System: …` mid-sentence stays a normal bubble; the role is untouched, so message counting, ordering and compaction see exactly the same history as before, and the card shows up identically in the resident history, the archived prefix after `/compact` and the subagent view (all three go through the one user-message render site).

#### Agent
- **A subagent that finished its work could be reported as `not_done`/`needs_context`** — the outcome parser scanned the **whole** report for words like "missing", "failed to" or "could not", so it read the errors a report *describes as fixed* ("the fixture file was missing, one test failed to compile before the fix") as proof that the run itself had failed, and the parent then re-dispatched work that was already done. A declared `STATUS:` line (or a JSON `status` field) is now authoritative against the heuristics: none of them may downgrade it, and only values outside the known vocabulary fall through to them instead of silently locking the outcome to success. A value outside the vocabulary that is nonetheless phrased as a declaration (`STATUS: could not complete the task, CI is red`, `STATUS: almost done but one test is red`) is classified by those same opening-line rules instead of being read as success, and that inference never outranks a real declaration. A later *declared* `STATUS:` can only lower the outcome — the last word of a report that revises its verdict down ("`STATUS: not_done, the last test still fails`") is honoured, while an echoed or quoted `STATUS: completed` cannot turn a downgraded run into a success. Declarations resolve on the **leading status token**, so a trailing clause cannot hide one — `STATUS: not_done (blocked by CI)` reads as `not_done` — and the near-miss vocabulary a model actually uses for unfinished work (`partial`, `partially_done`, `partially_complete`, `in_progress`, `wip`, `not_started` and their spaced variants) is `not_done` rather than an unknown value, so an explicit "I am not finished" declaration is not read as success; `pending` is deliberately on that terminal side too, although it can qualify work that is only awaiting a human "pending review by the user", because a `needs_context` dependency never reaches a terminal state and would leave every task waiting on it unsatisfied — the summary carries that nuance to the parent. The alternation guard that keeps a printed legend from counting as a declaration is now a legend detector rather than a separator blacklist: only a value whose alternatives resolve to two **different** statuses and include a success is a legend, so `STATUS: in progress (3/8 files done)` and `STATUS: not_done - pkg/tools/registry.go unreadable` keep their verdict (both used to fall through to the completed default) and `STATUS: blocked/pending - the CI token is missing` stays `not_done` (it used to be read as a legend and reported as `completed`), while `STATUS: completed | not_done | needs_context` is still a legend. A declaration is also only a declaration where the contract puts it: a `Status:` line in the middle of prose is narration about the work, and the contract template a model prints inside a ``` (or `~~~`) fence *before* its real header is a quote, not a verdict — both used to hijack the outcome. Declarations are decoration-tolerant, so `**STATUS: not_done**`, `## STATUS: not_done`, `- STATUS: not_done` and an emoji-wrapped value (`STATUS: ❌ not_done`) parse exactly like the bare line. `DETAILS:` is a terminal section, so a status quoted inside the body can no longer rewrite the outcome — with one deliberate exception: a status line that *closes* the report is the subagent's last word and is honoured **when the header declared no status of its own** (decoration lines — a trailing `---`, a lone emoji, an HTML sign-off comment — are skipped when finding that last line, so they cannot defeat the rescue), which keeps a genuine `not_done` from being reported as `completed`. The same deference applies to the two other shapes that used to hijack an outcome: a JSON document the report merely *pastes* (an example payload) no longer outranks the text `STATUS:` line, and the fences such a report uses are tracked the way markdown defines them, so a `>`/`-`-prefixed or `~~~` block, an unclosed wrapper and a quoted diff line (`+ ```go`) are all read as the body of the report instead of swallowing the declaration that follows. Output that never declares a status at all is now classified only by its opening declaration lines (the first five non-empty lines — three let a `#`/`Scope:`/`Files read:` preamble swallow the whole window before the declaration on the next line could be seen — ≤400 characters) with patterns that require a subject and a delimiter — "I could not complete the task", "Blocked: …", "Blocked on CI outage.", "Almost done but one test is red" — the delimiter being a terminator or a clause break, never a bare hyphen or an attributive noun, so prose about the code ("Blocked jobs are now retried", "Blocked-by-design queue jobs", "Task incomplete handling was added", "Partially completed orders are now resumed on restart") never masquerades as a declaration, and the inline `subagent` tool result no longer headlines every outcome as "Subagent task completed": its first line states the declared status.
- **A chat with read images could die on an oversized-request HTTP 400 and keep poisoning the session** — `read_image` injected the raw file bytes base64-encoded (up to ~27 MB for a single image), the token estimators counted those bytes as text, and nothing capped the outbound request, so a few images in history pushed a request past the transport's 10 MiB body cap; the turn aborted with `LLM call failed after retries` and every following turn resent the same blobs. Three user-visible consequences are fixed: `read_image` output is downscaled and re-encoded at the origin (long side ≤ 1568 px, at most 1.5 MiB encoded per image); every request is capped before it leaves the process — an 8 MiB byte budget with at most 4 live images, older media replaced by a text placeholder; and a request the transport still rejects for size now evicts the media and retries instead of aborting the turn, and the stored session is cleaned so the next turn cannot resend the blobs.

#### Session
- **A streamed assistant reply could be left flagged `streaming` in the middle of the history, and the WebUI then treated it as a live stream forever** — the flag `Streaming=true` was only ever cleared by `AddFullMessage`'s in-place branch (`pkg/session/manager.go`), which requires the incoming message to be an `assistant` **and** the tail to still be the streaming message. Every other writer that follows a streamed assistant appends a *non-assistant* message, so the flag was never cleared and the invariant "a `Streaming` assistant is only ever the last message" was broken. Four production routes did it, all in `pkg/agent/llm_runner.go`: **(P1)** the loop-detector guidance `AddMessage(sessionKey, "user", guidance)` appended immediately before the assistant message carrying the tool calls; **(P2)** the same guidance before a plain-text assistant answer; **(P3)** the malformed-tool-call guidance, where the assistant message is never persisted at all; and **(P4)** the early returns that end a turn mid-stream, which leave the streaming message as a legitimate tail — it only becomes a mid-history orphan when the *next* turn appends its `user` message (`llm_runner.go:245`), which is exactly the append this fix finalizes. The orphan sat in the middle of the history with `Streaming=true`, written to SQLite and surviving restarts, and no reader is prepared for it: the WebUI hid the "thinking" dots on **every later turn** (`MessageList.tsx`, `!messages.some((m) => m.streaming)`) and stopped parsing markdown for that bubble (`MessageBubble.tsx`, blocks are skipped while `streaming`). The flag itself never reached the model — `providers.Message.Streaming` is not part of the wire format (`SerializeMessages`) — so the damage is a broken invariant plus a permanently wrong render, not a bigger prompt. The fix resolves the tail in the session layer, at the single append funnel: before appending a non-assistant message, `AddFullMessage` calls the new private `resolveStreamingTailLocked`, which finalizes a tail that already carries content **in place** (same position, same content, only the flag flips) and reuses the slot of an empty placeholder. The order does not change — nothing is reordered, moved or deleted, the runner's live in-memory `messages` list is untouched, and when the tail is not a streaming assistant the append is byte-for-byte identical to before — so a crash-recovery orphan stays **visible** exactly as `pkg/channels/rest_chat.go` requires (it only hides a streaming message while the session is processing) and is finalized by the next turn's user message instead of being dropped silently. Reusing the placeholder's slot is deliberate: `RemoveLastMessage` would have composed its `deleteFromSeq` watermark with the `msgsAppended++` of the same call, and it re-takes `sm.mu` (not reentrant) from an already-locked caller. This is a **pre-existing bug** and the fix applies to new writes only: **histories already corrupted on disk are not repaired** — an existing orphan is finalized the next time a non-assistant message is appended after it, but nothing sweeps history proactively. Two residuals are deliberately left alone, both pre-existing and untouched by the flag clearing: the finalized message keeps its content, so when the same text was also persisted on the tool-call assistant message the two copies still coexist in history and both are still sent to the model; and nothing already on disk is rewritten.
- **Eviction could empty all resident context** — the in-memory eviction boundary used the last `ExcludeFromContext=true` row across the entire slice, so a trailing approval/rejection row written by `persistApprovalMessage` (`pkg/channels/rest_chat.go`) with `ExcludeFromContext=true` in the queue dragged `evictUpTo` to `len(Messages)`, wiping all resident context. Eviction is now clamped to the compaction boundary (`excludeBoundary`, the `hi` of the range `ExcludeOldMessagesFromContext` computed), which survives the `SetHistory` call in `summarizeSessionCore` so the clamp applies in every subsequent compaction round, with fallback to the contiguous excluded run at the front when no boundary is recorded (cold load, where `excludeBoundary` is in-memory only and is not persisted). A structural invariant further guarantees that eviction never empties the entire resident slice: when the anti-split guard in `ExcludeOldMessagesFromContext` pushes the boundary to `len(Messages)` (session tail is a tool-result group), the invariant caps eviction at the last non-excluded message so at least one context message survives in RAM.
- **Summary folded the previous summary message** — `foldEvictedIntoSummary` also folded the summary-message the agent injects (its content already *is* `session.Summary`), producing a nested `## Summary of Previous Conversation` header with duplicated body and growing the summary ≈2× per compaction round (measured over a pre-#339 baseline in a 6-round probe via the production path; in the current base the skip of the summary marker already bounds growth) instead of staying bounded. The summary message is now skipped.
- **Exclusion range could be empty** — the range clamp (`hi <= rangeStart`) could yield `[0, 0)` when the only mutation was un-excluding index 0, which caused `saveUnlocked` to skip the targeted `UpdateMessagesExcluded` and leave index 0 persisted as `excluded=1` in SQLite even though memory said otherwise (re-excluded on reload). The semi-open range now always includes the index that changed.
- **The no-op eviction was not free and not honest** (#343, INFO-1) — the #340 structural invariant caps `evictUpTo` at the last in-context message, and when that message is index 0 the cap yields `evictUpTo == 0`: nothing is evicted. That is the right outcome (the alternative is emptying the resident context) and it recurs — the anti-splice guard of `ExcludeOldMessagesFromContext` walks its boundary past a tail of tool results, so a session whose whole history except the pinned first human turn is excluded is a normal compaction shape, measured at 61 of 957 swept layouts. But it still paid a SQLite round trip writing a `FirstInMemorySeq` that had not changed, bumped the epoch and republished the copy-on-write history view for byte-identical content (invalidating every `GetHistoryView` reader's snapshot for nothing), and logged `Evicted excluded messages from memory {evicted=0}`, which reads like an eviction happened — on the path every compaction takes. Short-circuited before the I/O; safe because with `evictUpTo == 0` the value is unchanged by construction and a cold load rebuilds `firstInMemorySeq` *from* the row, so memory and row cannot diverge on this path. The phase-3 bookkeeping is replicated, not dropped: `clearDirtyFlags` + `lastPersistedSeq = len-1` is what makes the next `Save` idle instead of rewriting the whole history, and losing it would have turned a cosmetic cleanup into a durability-path regression. The **retention policy is deliberately unchanged** — #343's other option (move the boundary back, keep the whole tool group in context) removes both remaining costs but changes what the model sees and needs a token measurement first; a test now pins what today's policy keeps in RAM (3 excluded rows resident, 1 message reaching the model) so changing it is a deliberate edit to a stated number rather than an accident found in a profile.

#### Native
- `lele client pin` generated a PIN that the server rejected with 400 `invalid PIN` since #326 — #326 added `SetStore()` to the CLI so `client list`/`remove` could see the server's paired clients, which put the CLI on the SQLite branch of `saveStoreUnlocked()`: that branch persists `Clients` and returns before writing the JSON (`auth.go:241-263`), so pending PINs stopped being written **anywhere** and died with the CLI process; the CLI→server handoff was `native_clients.json`, which the server still re-reads on redeem. Pending PINs now live in the shared SQLite DB (`native_pending_pins` table, migration v6→v7) with atomic single-use redeem across processes (`DELETE … RETURNING` with the expiry predicate in the same statement); the JSON merge hack in `loadStore` and `PairWithPIN` is eliminated. **Replay bug found while reproducing**: a JSON-origin PIN was redeemable **5 times** — 5 `client_id`/tokens — because the merge resuscitated the already-deleted PIN from the stale JSON (never re-written in SQLite mode); the only thing that stopped it was `MaxClients=5`. Server/WebUI PINs were always single-use; onboarding PINs (`lele onboard`, `onboard.go:587`) were not. All are now. Pure JSON mode (`repo == nil`, desktop and mips64 without SQLite) is unchanged: `maxPendingPINs`=10 with purge-then-evict, `/api/v1/auth/pair` error texts and rate limits unchanged, no changes in `web/`. **Rollback note**: an older binary starts against a v7 DB without error but won't see pending PINs — losing pending PINs on rollback is harmless (TTL 5 min). Related: #327 (client revocation unreliable via snapshot sync of `saveStoreUnlocked`, deliberately out of scope), #328 (`channels.native.lele_dir` ignores `LELE_CONFIG_DIR`, deferred, zero production impact).

- **Revoking a client from the CLI did not stop it authenticating** (#327) — two halves, and the merged fix for the first left the second standing. (a) `saveStoreUnlocked`'s SQLite branch was a *whole-store snapshot sync*: it re-upserted every client in the calling process's map and **deleted** every table row absent from it, so with gateway + CLI sharing one DB, each process's map is a stale view and any gateway write (`GeneratePIN`, `PairWithPIN`, `RefreshToken`, `TrackSessionKey`, `RegisterDesktopClient`) resurrected what the other had just revoked — last writer wins with the whole map. Production mutators now write single rows (`persistClientLocked`, `repo.DeleteClient`); `saveStore()` survives only for migrations and tests, and a characterization test pins that the clobber is still there, because what changed is *reachability*, not behaviour. (b) The reported impact outlived (a): `ValidateToken` answers a map **hit** without ever consulting the DB (it reloads only on a *miss*, `slowReloadMinInterval`), so `lele client remove` deleted the row while the running gateway kept waving the token through until it restarted. `AuthManager.reconcileClientsWithStore` now drops every in-memory client whose row is gone, every `authReconcileInterval` (15 s) from `NativeChannel.Start`, and tears down the WebSockets those clients already hold — a revoked device still streaming is not revoked either, and its token was validated once at handshake. Deletions **only**: adoption is the reload-on-miss's job, and copying DB rows into the map would revert an in-memory rotation whose persist failed; a reconcile that could *add* rows would reintroduce resurrection in a new place. The shared read happens outside `am.mu`, so authenticated traffic never waits on the query. Consequence accepted and documented: a client whose directed write failed (SQLITE_BUSY, full disk) now drops after the interval instead of living on in memory — which is what "the DB is authoritative in SQLite mode" means, and the first cache-miss already erased it via `loadStore()`.

- **A degraded gateway answered `400 invalid PIN` for a PIN it could not read** (#330) — `cmd/lele/gateway.go` logs one warning when the shared SQLite store will not open and carries on with JSON storage. On a no-SQLite build that fallback is correct and load-bearing; on a SQLite-capable build whose DB is locked, unreadable or on a full disk it leaves the gateway half-alive, and the CLI had already written the pairing PIN into that DB — so the gateway looked the PIN up in `native_clients.json`, found nothing, and told the user their credential was invalid, forever, pointing at the client for a server-side storage fault. The asymmetry was the proof: `newClientAuthManager` (CLI side) already refused explicitly in the same situation. `AuthManager` gained an explicit degraded state kept **separate** from `repo == nil` (a nil repo is also the legitimate steady state without SQLite, where JSON *is* the shared backend and pairing must keep working untouched): `SetStoreUnavailable`/`StoreUnavailable`, `GeneratePIN`/`PairWithPIN` refusing with `ErrPairingUnavailable`, the REST layer mapping that to `503` + a `store_unavailable` code distinct from `pair_error`/`pin_error`, `GET /api/v1/system/status` reporting `storage: {backend, degraded, error}` so a gateway on the wrong backend is diagnosable from outside instead of only in its own log, and `Manager` re-applying the condition after `ReloadConfig` rebuilds the channels. `SetStore` with a non-nil repo clears it, so a re-wired gateway recovers.

- **`channels.native.lele_dir` baked a `$HOME` path into `config.json`** (#328) — its default came from `getDefaultLeleDir()`, derived from `$HOME` and blind to `LELE_CONFIG_DIR`, while the gateway opened its SQLite store at `config.GetLeleDir()/lele.db`: one process kept its auth store in `$LELE_CONFIG_DIR` and its `native_clients.json` in `~/.lele`. Defaulting the field to `GetLeleDir()` is the obvious fix and it is wrong here, because **defaults are persisted** — `SaveConfig` marshals the whole struct and `lele_dir` is only `omitempty`, so any non-empty default lands in `config.json`, and a value in the file beats the code default on load. One sandboxed or CI run with `LELE_CONFIG_DIR` set would have pinned that scratch path into the user's config and relocated the auth store, uploads, attachment staging and the skills dirs for every later run without the env var. The field now stays empty and is resolved per run by `NewNativeChannel` (the same lazy idiom as `WorkspacePath`, `LogsPath`, `KeyringVaultPath`), into its *own* copy of the native config: uploads and staging read `n.cfg.LeleDir` directly, so leaving it empty would build `tmp/uploads` relative to the process cwd, and writing back into the shared `*config.Config` would re-create the freeze the empty default avoids. An explicit `lele_dir` still wins.

- **A config reload left the retired channel's background loops running forever** — `Manager.ReloadConfig` stops the old channels with `channel.Stop(m.runCtx)` and builds replacements, but `m.runCtx` is the process context and a reload never cancels it. `NativeChannel.Start` had launched its periodic loops (`runUploadCleanup`, and since #361 `runAuthRevocationReconcile`) under exactly that context, and `Stop` cancelled nothing — so every reload leaked one goroutine per loop, kept the whole discarded `NativeChannel` reachable from them, and left a ticker polling SQLite every 15 s for the life of the process. Reloads are not rare: saving the config from the WebUI or the desktop app goes through `SetReloadConfig` → `ReloadConfig`. The channel now owns a lifecycle context created in `Start` and cancelled by `Stop`, which joins its loops before returning. The join deliberately happens **after** `n.mu` is released, because a reconcile tick takes that same lock to drop the WebSocket of a revoked client: joining under the lock would have turned every reload landing on a tick into a deadlock (pinned by a test that measures `Stop`'s duration against the join budget rather than asserting the outcome, since both orderings eventually free the lock). The hourly upload sweep had the same leak at 240× lower cost, which is why it went unnoticed; it is bound to the same context now. `authReconcileEvery` makes the 15 s interval overridable per channel so the loop's wiring — not just `reconcileClientsWithStore` in isolation, which #361 already covered — is testable.

#### WebUI
- **The chat log had irregular vertical spacing, with dead bands between tool cards** — every assistant message rendered as a row with `py-3` (24px) whether or not anything inside it was visible, and the per-role paddings were ad-hoc (`py-1` user, `py-1.5` tool, `py-3` assistant), so the gap between two rows depended on which kinds happened to be adjacent (10/12/16/18/24px in the same conversation). Pinned by `MessageBubble.visibility.test.tsx`, `MessageBubble.rhythm.test.tsx` and `lib/chatRowSpacing.test.ts`.
- **The chat list re-ordered itself again mid-session, and this time the pairing was architectural** — `mergeMessages` matched a live WebSocket assistant to its persisted twin **by position** ("the Nth live assistant from the end is the Nth base assistant from the end", `computeMatchOffset`). That count invariant cannot hold in the real event stream, because two independent conditions break it and each one shifts the pairing by a slot: (1) `handleHistoryUpdated` strips a turn's live copies only once the `history.updated` refetch lands, so a snapshot can still hold the **previous** turn's live copies while `base` already contains them, and (2) the backend persists every LLM iteration as its own assistant message, so a turn running a tool whose first iteration already finished contributes a **completed** live assistant (`streaming: false`) that `base` does not have yet. With one extra completed copy the matcher paired `a1↔t2`, `t2↔a2`, `a2↔t3`, transferring each one's `stableId` — the React render key — so the bubbles swapped keys and Virtuoso moved them: the visible list re-ordered itself, and only a reload (which clears `streamingMessages`) put it back. Reproduced against a real gateway + real WebSocket stream in Chromium with the new opt-in `lib/orderingMonitor.ts`: **8 `stable-order` violations from turn 3 on** before, **0 over 202–266 merges** after. All positional matching is gone (`computeBaseHasCurrentTurn`, `computeMatchOffset`, `pairCompatible`, the `streamAsstIdx` cursor): `findStreamingTwin` pairs by **content identity** (`lib/messageIdentity.ts`) in two tiers — byte-identical first, then "the live copy is a prefix of the persisted one" (a turn can end between two renders) and only when that live identity is **not** already rendered from another base assistant, which is exactly the shape that used to donate a key to the wrong bubble. Only the React key is transferred; the persisted copy stays authoritative and keeps its server-side slot. Pinned by `web/src/hooks/messagePairing.test.ts`, which rebuilds the recorded browser snapshot (two finished turns in base, the third running a tool, the previous turn's live copies not yet stripped) and fails on the old matcher with `answer number 1` inheriting `live-t2`'s key.
- **The ordering bug is now diagnosable instead of guessable** — "the order breaks after a while" had been investigated several times without a reproduction, so the browser collects the evidence itself: `lib/orderingMonitor.ts` is an opt-in, in-memory ring buffer (one boolean check per merge when off) of every WS event, every history snapshot and every merge, checking the four invariants whose violation *is* the bug — `stable-order` (two messages that both existed in the previous render flipped), `duplicate-key` (two entries share a render key), `base-order` (canonical history came out re-ordered) and `stranded-copy` (a live copy rendered as its own entry while history already holds the message). Wired at the three points that matter (WS dispatch, history poll, merge result) and documented under "Message Ordering (maintainer notes)" in `docs/web-ui.md`.

- **A long chat lost its order "after a while" until the page was reloaded** — every LLM iteration that produces **no text** (a thinking step, or the tool-call step of any model that does not emit text alongside the call) is persisted as its own assistant message with `content === ""` and its payload in `reasoning_content`, and the WebUI kept its *live* WebSocket copy in `streamingMessages` forever: the confirmation that strips a live copy once history holds its twin matched on a **content prefix**, and an empty prefix never matches. One immortal leftover accumulated per tool/thinking iteration, and once the conversation passed 50 messages the backend's sliding history window (`pkg/channels/rest_chat.go`, `resultStartIdx := endIdx - limit`) had already evicted the twin, so `mergeMessages` could no longer pair a leftover with anything and appended it at the **end of the list** — old "Thinking…" blocks rendered *below* newer answers, one more per turn, with the whole visible window shifted around them. Reloading cleared streaming state, which is why a refresh showed the correct order. The identity of a text-less iteration is now its reasoning text instead of its (empty) content, in one place — `web/src/lib/messageIdentity.ts` — consumed by all three sites that must agree: `isConfirmedInCache` (strip), `messageMerge`'s pairing/dedup, and `toChatMessages`'s durable React-key registry (so the swap from the live UUID to the canonical id does not remount the bubble either). `handleHistoryUpdated` additionally drops a COMPLETED iteration that has neither text nor reasoning — the shape `filterStreamingLeftovers` already dropped at render time — because it could never be confirmed and leaked one entry per tool iteration for the life of the session. Pinned by `web/src/hooks/chatPipelineOrdering.test.ts` (20 turns of thinking+tool turns through the real WS handlers, real `history.updated` strip and real merge: the merged order must equal the served window on every turn — 8 of 20 turns and up to 13 stranded blocks before the fix, `maxStreaming` bounded to the current turn after), R8/R9 in `messageOrderingWindow.test.ts` (no duplicate iteration; the persisted copy reuses the live React key) and a real-Chromium scenario in `e2e/ordering.e2e.ts`.
- Messages with identical content collided on one ID, reordering and erasing bubbles in the chat pane — the wire ID of a resident in-memory message is a content hash (`role|content|tool_call_id|tool_calls`), so two genuinely different messages with the *same* text (a repeated question, a repeated answer, a retry that produced identical output) received the *same* ID. Four defects chained from that single collision: (1) the history builder treated the repeat as a backend re-emit and **dropped it**, so four server messages rendered as three bubbles and the surviving answer sat above the wrong user message; (2) the stable-ID registry stored one ephemeral ID per content key, so the second registration overwrote the first and React saw duplicate keys, silently dropping a bubble on the WebSocket→HTTP transition; (3) `before_id` pagination resolved to the *first* occurrence, jumping the viewport to the wrong position; (4) two sends inside the same millisecond shared a `temp-user-<ts>` optimistic ID. ID generation is now occurrence-aware: the first occurrence of a content key keeps the historical `<sessionKey>:<16 hex>` form and later occurrences get a `-<n>` suffix, so the id *format* is unchanged — but the digest the id embeds is a new one, and that changes the id *value* of every resident message (see the upgrade note in the next bullet); the registry and the history builder track occurrence indices so each copy keeps its own ephemeral ID; and optimistic user IDs are forced monotonically increasing. Two rapid sends no longer pair a completed answer into an older base slot either: when the base has not yet caught up with the newest turn, positional matching is replaced by content-confirmed matching, so an answer with genuinely new content is never rendered above a previous user message, while a copy already present in the base is still deduplicated instead of appearing twice.

- **Resident message ids change value on the upgrade (one-off)** — the wire id of a resident message is still `<sessionKey>:<16 hex>[-<occurrence>]`, but the 16 hex characters are now a bounded 64-bit FNV-1a digest over the role, the content length, a sampled window of the content and the tool-call identity fields, where `residentMessageKey` used to truncate a SHA-256 over the full content. Bounding the digest is what keeps `GET /api/v1/chat/history` from copying and hashing ~15MB per request on a large session (~3.5k resident messages, 50 returned), and it is only acceptable because that key is a UI identity, not a security primitive: two messages that end up sharing it are treated as occurrences of one identity and still receive unique ids. **Upgrade note**: every id embeds that digest, so the ids of *every* message in *every* session change value at the upgrade — not only the ids of messages with identical content; a cursor minted by the previous binary therefore no longer resolves for a tab that is mid-scroll when the server is upgraded. The effect is bounded and is exactly the documented stale-cursor behaviour: an unmatched `before_id` falls back to the newest resident page (and continues into the evicted region once the resident window is exhausted), so the visible symptom is that older pages may appear once more until the tab is reloaded; no message is lost and nothing else changes. The API shape, the `limit` bounds (default 50, max 200), the `before_id`/`has_more` cursor semantics, the `evicted:<seq>` cursor form and every status/error code are unchanged, and ids stay stable within one version.

- **The sidebar re-fetched the whole session list several times per turn** — `refreshSessions()` walks the *entire* paginated `GET /api/v1/chat/sessions/meta` loop (two requests as soon as a user has more than 200 chats, which is the reported `?include_system=true&offset=200&limit=200` seen 5+ times in a row), and it was triggered from four independent paths with no coalescing: the bootstrap on mount, every `disconnected|connecting → connected` WebSocket transition, the session-event debounce in `useMessages` (fed by `history.updated`, `message.ack` and `message.complete`, so a single turn that uses tools fires it several times in a row) and `clearSession`. Three layers now bound the cost, all client-side — the pagination itself was legitimate and the backend is untouched: (1) a React-free single-flight coordinator (`web/src/hooks/sessionRefreshCoordinator.ts`) keyed on a generation counter, where concurrent triggers join the pass in flight instead of starting their own, a re-trigger of the *same* task starts nothing, a genuinely different task schedules at most one trailing pass, and a failed pass drops the coalesced work rather than chaining retries; (2) the WebSocket handler only runs its recovery on a *real* reconnection (`hadWsConnectedRef` tells it apart from the first connection, which the bootstrap already covers), and the list is revalidated when the tab becomes visible again, so removing that duplicate costs no freshness; (3) the event debounce is a leading+trailing throttle with a 5 s window and one queued trailing call per window — the leading edge keeps a brand-new chat appearing instantly, the trailing edge guarantees the final state of a burst is reflected. `reset()` (logout, agent switch) bumps the generation, so a slow in-flight pass can neither ask for its next page nor write another user's chats into the post-logout UI.

- **The boot wave left the WebUI with no `Authorization` header and burned a single-use refresh on every page load** — `createApiClient()` was constructed with `token: null` and `AuthProvider` installed the stored credential from a `useEffect`, but React flushes CHILD passive effects before PARENT ones, so every descendant's first request was already in flight when the token landed. The gateway answers a headerless protected request with `401 auth_missing` without ever consulting the stored session, and each such answer spent a `POST /auth/refresh` — which is single-use and kills the previous access token immediately, because `ValidateToken` never honors `PrevTokenHash` (refresh tokens got a replay window in #354; access tokens did not). Measured on a production gateway log: 728 `auth_missing` against 37 `auth_invalid_token`, so the storm was missing headers, not expired credentials. The credential is now seeded synchronously at client construction (`createApiClient(baseUrl, initial?)`, fed from the session of the render that builds the memo, so pairing against a *changed* API URL in the same commit as the new session still produces an authenticated first wave). Session *changes* still arrive through the existing effect, and the memo's dependency list is deliberately unchanged (`[apiUrl, detachSession]`): recreating the client on every session change would discard its single-flight, cooldown and cross-tab adoption state.

- **A 401 for a credential that had already been replaced spent a second rotation** — when a rotation lands while a request is in flight (proactive renewal on mount or on the 24 h interval, another tab's rotation adopted here, or the refresh a neighbouring request triggered), the server has already killed the bearer that request carries, so the 401 says nothing about the credential we hold now. The retryable JSON path used to answer it with another `POST /auth/refresh`, wasting a single-use rotation on a credential that was never dead — and every wasted rotation invalidates the access token that other in-flight requests, in this tab and in others, are still carrying, which manufactures further 401s. Such a 401 is now answered by replaying the request once with the credential actually held, consuming neither the refresh flag nor the retry budget, so a genuinely dead credential still reaches the refresh path; bounded to one replay per call. The boot wave now leaves authenticated with zero rotations spent, and the three call-sites that hand-roll their own `fetch` (`fileBlob`, `uploadFiles` and the chat SSE stream) inherit the header fix from the seed even though the replay still applies only to the retryable path; they are tracked separately. Covered by `web/src/contexts/AuthBootstrap.test.tsx`, which mounts the real `<App/>` against a gateway mock that answers headerless protected requests the way the real one does, including under `<StrictMode>` as `main.tsx` mounts it. Dead duplicate `web/src/hooks/useAuth.ts` (170 lines, zero importers) removed along the way.

- **A historical subagent was labeled with an arbitrary agent** — the chat header and the subagents panel name a subagent's agent from the `subagents` listing, and the *persisted* half of that listing filled `agent_id` with the agent whose session storage was being swept, not the one that ran the task. Since every agent shares one `SessionManager` in production, `FindSubagentSessions` returns the same rows for each registry agent and the first one won the `seen[]` dedupe, so a subagent opened after a gateway restart (or already finished and reaped from memory) showed the default agent instead of its target — visible since #331 made the header consume the field, though the live path was the only one that ever reported the truth. The executor is now persisted on the session row itself (`sessions.agent_id`, migration v7→v8), written by the spawn-time session-key callback that already knew `task.AgentID`, and rows written before the column fall back to the durable `sess:agent:` routing pin and only then to the storage owner, so upgrading does not leave existing history mislabeled.

#### Providers
- **A migrated provider credential could be dropped when a keyless entry already existed** — `lele migrate` (importing another tool's config) merges into the existing `config.json` through `MergeConfig`, which wrote a provider's key into the **typed** copy only (`Providers.Anthropic`, `Providers.OpenAI`, …). A config whose `providers` section already held a keyless entry for that provider (`api_base`/`proxy` only — a local endpoint, or an OAuth-completed session) then serialized from the **named** copy, and `MarshalJSON` skips the typed copy for a key that already exists in it, so the migrated credential never reached disk and the import looked successful while leaving no usable provider. The merge now mirrors the fields it writes into the named copy, filling only the empty ones (an existing named value wins, and `models`/`auth_method`/`connect_mode`, which live in the named copy, survive the merge).
- **A configured provider could be erased by the very next save** — `pkg/tui` decided "this entry is disposable" by looking only at the API key, the model list and the auth method, so a provider whose configuration lives elsewhere on the entry — a keyless local endpoint (`api_base`/`proxy`, the supported "API key is optional for local providers" case: ollama, vLLM, LM Studio) or an OAuth-completed entry (`auth_method` plus `connect_mode`) — looked empty and was overwritten wholesale by `/connect`, by the onboarding wizard and by the OAuth persist path. `ProvidersConfig.MarshalJSON` had the mirror-image bug and *dropped* those entries from `config.json` on the next save even when nothing in the UI had touched them. Both now share one predicate, `NamedProviderConfig.IsEmpty()`, which counts every field that can only come from a user edit (`api_key`, `api_base`, `proxy`, `auth_method`, `connect_mode`, models) and deliberately ignores the two fields the loader pre-fills for every known provider (`type`, and OpenAI's `web_search` copy), so empty placeholders stay unpinned while a configured entry is never silently discarded.
- **`alibaba_coding_plan` shipped a hard-coded default endpoint** — `DefaultConfig()` carried `https://coding-intl.dashscope.aliyuncs.com/v1` in the typed field, which made the provider look *configured* (so it was written to `config.json` and counted as user data) and silently pointed users at the international gateway even when their plan lives elsewhere. The default is gone; the base is resolved from the provider preset when the flow needs it, exactly like the sibling plan providers.
- **A human message between a tool call and its result discarded the real result** (#337) — `HealToolCallPairs` closed an open tool block on any message of another role, so a user turn recorded between an assistant `tool_use` and its `tool_result` synthesised *"No recorded result for this tool call … Re-run the tool"* for a call that **did** have a result, and the real result was then dropped as an orphan when it arrived. The model was told to re-run tools that had already run — including side-effecting ones — and the history came back reordered on top. Nothing was lost on disk; the damage was in the request sent to the provider. The default case now buffers a message of any other role while a block is open and emits it after the results, the only position a provider accepts it in; a call whose result never arrives still gets the placeholder, so genuine truncation keeps its old behaviour. Two invariants held on purpose: a valid history returns element-for-element identical, and orphans/duplicates/out-of-order results are still rejected by the "only the open block may answer" rule — both now covered by subcases. The pre-existing case "result interrupted by a user message stays attached" missed it because it asserted only *roles*, and the synthetic placeholder is also role `tool`; it asserts the content now, and fails against the previous healer.

#### Heartbeat
- **A stopped heartbeat loop failed unrelated CI jobs** (#338) — a loop still alive when a test ends keeps recreating `HEARTBEAT.md` inside the temp dir *while* `testing` removes it, so the `t.TempDir()` cleanup walk fails with "directory not empty" and the Tests job goes red for a reason unrelated to the change under review. The window is milliseconds wide, which is why it never reproduced locally and cost a diagnosis run every time it struck a random PR. `UpdateConfig` was the leak: it disabled the loop by closing `stopChan` and dropping `hs.done` on the floor, leaving the signalled goroutine unreapable — a later `Stop` saw `stopChan == nil` and returned immediately while the goroutine was still inside a beat and still holding the workspace. Disabling now parks the done channel (`stopLocked`) and `Stop` waits on every parked one; `UpdateConfig` must not block on an in-flight beat, which is why it parks rather than waits. Regression coverage is timing-independent — a handler blocked across a disable+Stop, asserting `Stop` does not return before the goroutine is gone — and it fails against the previous `service.go`. Every test that starts the service now defers `Stop`; only one had been seen failing, the pattern was shared by six.

#### MCP
- **A server one chat loaded appeared in every other chat's tool list** — `load_mcp_tools` registered the remote `mcp_*` tools into the agent's `ToolRegistry`, and that registry belongs to the *agent instance*, shared by every session it serves (native, TUI, Telegram, WebUI tabs, group turns). So the moment chat A loaded a server, chat B's tool definitions grew with tools B never asked for — and B could call them. Worse, it was sticky: the names stayed until the server vanished from `mcp.json` or the process restarted. The load is now **session-scoped**: each session gets a scoped tool registry (`tools.NewScopedRegistry`, a layer over the agent's base registry, live — never snapshotted, so a reload still reaches it), `load_mcp_tools` and the tools it registers live in that layer, and the base registry is never touched. Tool definitions, execution (`toolExecutor` now resolves through the session's view, not `agent.Tools`), group turns, the plain-text tool-call heuristic and `updateToolContexts` all read the same layer, so a load is visible to exactly the session that performed it and to nothing else; a stray call from another session fails with `tool "…" not found`. The layer is stable for the session's lifetime (a load survives later turns) and is dropped when the session is cleared (`/clear`, `/new` — where the abandoned conversation key is dropped too) or when the agent's MCP manager is retired (`mcp.json` lost its last server, the workspace moved, the allowlist stopped allowing the loader, shutdown, manager replaced): a layer's loader closes over its manager, so it must never outlive it. The per-entry `nameSet` bookkeeping (which existed only to unregister names from the shared registry) is gone — dropping the layer is the whole retirement. Layers are capped at 256 per agent with LRU retirement so a long-lived gateway cannot accumulate them. Regression tests: `pkg/tools/registry_scoped_test.go` (layer semantics, shadowing, live base, flattened clones) and `pkg/agent/mcp_session_scope_test.go` (session A loads → B's definitions and calls are unaffected; same-session stability; `dropSessionTools` isolation; executor wiring; teardown drops every layer).
- **The management surface could be blind to a live server** — the raw reader (`pkg/mcp/rawdoc.go`, the expansion-free parser that feeds the inventory, the validation gate and both UIs) kept only the **last** top-level `"mcpServers"` occurrence and matched the envelope key **case-exactly**, while `encoding/json` — the runtime's own decoder, reached through `ParseFile`/`Discover` — decodes every occurrence into the same map (a **union**, per-name last-in-file-order wins, a `null` occurrence clears what came before) and matches struct fields case-insensitively. Measured on the pre-fix tree: `{"mcpServers":{"a":…},"mcpServers":{"b":…}}` gave the runtime `[a b]` and the reader `[b]`, and `{"MCPServers":{"c":…}}` gave the runtime `[c]` and the reader `[]` — so `a`/`c` were served to the model while the panel showed no row, no owner, no shadow info and no writable target for them, and `ValidateRawJSON` answered *valid* for a file `ParseFile` then refused, letting `PUT /api/v1/mcp/{layer}/raw` write a config the agent could not load. The reader now mirrors the runtime's rules and the writer follows the same fold (`lastMember` case-insensitive, `envelopeContaining` bounds a pure-stub deletion to the envelope that actually holds the winner — splicing against the cross-occurrence fold used to **collapse two envelopes into one** and drop the other's servers). Pinned by differential oracle tables that compare our verdicts with `encoding/json`/`ParseFile` over the *same bytes* (`TestRawDocEnvelopeMatchesRuntime` 13 rows, `TestWriteEditDifferentialNameSetAndValues` 9 rows with golden bytes, `TestValidateRawJSONParityWithParseFile` 20 rows) rather than pinning today's behaviour.
- **An empty or broken `mcp.json` was a dead end in the WebUI** — the panel early-returned an "no servers" card whenever the inventory had zero servers, which also hid the layer list, the inventory **warnings** and every edit affordance: with `{}`, an absent file or a malformed file there was no way to open the raw editor to type the first server, and a broken config rendered as a calm empty state that swallowed the very diagnostic the panel exists to show. The empty state is now a row *of* the panel, never a replacement for it.
- **A write that landed was reported as a failure, and could echo someone else's bytes** — `handleMCPRawPut` re-read the file *after* the atomic save and the reload had already fired, so a read error turned a successful, already-live write into `500 mcp_read_failed`, and a concurrent writer (TUI toggle, another tab, an editor) winning the rename/read race made the `200` response carry **that writer's** content as the result of this save. It now returns the bytes it wrote, because `SaveRawFile` is atomic.
- **The raw GET had no path guard while both write routes did** — `GET /api/v1/mcp/{layer}/raw` answered `200 path:"/not-allowed-root/mcp.json"` for a layer file outside the allowed workspace roots, where the PUT and the toggle refused the same file with `403`. One `mcpGuardLayerFile` now covers the raw GET (before any read), the raw PUT (before decode) and the toggle (before write), and `IsAllowedWorkspacePath` is exported so the TUI applies the identical rule instead of a copy that can drift.
- **A toggle could hide a broken entry behind an intentional-looking state** — an entry whose effective verdict is `invalid` was toggleable: `enabled` was computed as *FLIP* (`effective !== "enabled"`) instead of *SET*, so the write put `"disabled": true` into a broken entry and the verdict derivation, which prefers `Disabled` over `Invalid`, reported `disabled` — the diagnostic disappeared. In the TUI the same flip on an entry carrying a literal `"disabled": false` **deleted the entry**. Invalid entries are now not toggleable in either direction, enforced by the API (`400 mcp_entry_invalid`) as well as by both clients, and the only repair path is the raw editor; a toggle that answers `changed:false` is reported as "no change" instead of wearing success, and no client guesses a verdict locally.
